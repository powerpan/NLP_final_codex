# Token 用量分析與上下文修正

優化前版本已先上傳到指定的 [NLP_final_codex 倉庫](https://github.com/powerpan/NLP_final_codex/commit/07f9b5bf6dd7c9844633f498f67f71c40d97a486)。這個基準不含 key、資料庫、模型私密對話或原始 reasoning。以下分析使用本機保存的 API 用量與唯讀資料庫，沒有為了取得統計重新呼叫模型。

原先使用者新聞任務的 35 次請求、325,989 tokens 不在上述合計。它的部分失敗請求沒有保存 cache 細項，因此比較其 cache rate 時必須同時看資料覆蓋率。

新聞任務最值得改善：researcher 的 15 次請求用了 363,521 輸入 tokens，占該任務輸入 92.78%；單次輸入從 3,375 漲到 37,661。planner 的核對也有成本，但不是最大來源。協作 c 的總用量分布為 researcher 35.8%、reviewer WORK 26.8%、planner 22.0%、coder 14.1%、REPLY 1.3%；這份紀錄沒有顯示競標或唯讀 Agent 諮詢是主要浪費。

## 根因與修改

**變動狀態放得太早，破壞可重用前綴。** 上一輪為解決日期錯誤和證據交接，加入每次更新的時間、剩餘預算與證據索引，卻把它們插入首條 system 訊息。後面很長的工具歷史即使相同，前綴已經不同。這是當時修復帶來的成本退化。

現在固定能力與規則留在穩定的前段，最新狀態使用尾端、暫時的 system 訊息；不寫入持久歷史，也不偽造新 user turn。DeepSeek 的[前綴快取規則](https://api-docs.deepseek.com/guides/kv_cache/)支持這個方向，但快取屬於盡力服務，不能保證固定命中率。當前工具鏈的全部 assistant／reasoning／tool pairing 都保留，遵守[thinking 工具往返要求](https://api-docs.deepseek.com/guides/thinking_mode/)。

**同一證據的內容與索引重複。** 同一個已保存操作或同一頁完全相同的讀取，保留第一份正文，後續觀測留下原 tool ID、來源 operation ID、offset 與本地讀取方式。重複 URL 中繼資料只在完整 URL 已存在於同一觀測時省略；唯一來源、日期、正文與引用網址不裁掉。原始工具結果與資料庫不改寫。

**公開答案又被存成經驗帶回。** 記憶只去除同一輸入內逐字相同的內容；自動經驗的 summary 若與已帶入的 session 答案完全一致，改為明確索引，保留驗收、失敗原因和結果狀態。不同 reviewer 的經驗或不同版本不合併。

**用量記錄無法直接看成本組成。** 終端與評測現在同時呈現輸入、輸出、快取命中與覆蓋率；截斷、超時及協定失敗也保存已收到的計數。每次請求另保存僅含數字的上下文字元統計，方便區分工具 schema、system、user、assistant 和 tool 結果。這些是字元數，不能冒充 tokenizer 或帳單。

## 沒有採用的捷徑

新聞 b 的 8 次搜尋與 10 次抓取參數各不相同。8 次搜尋取得 80 個結果，涉及 74 個不同 URL，因此不是大量完全相同的外部請求。不同查詢可能有語義重疊，但沒有足夠證據把它們視為可直接刪除。原本同工作流成功請求的精確快取保留；失敗、執行中或結果未知的操作不假裝成功重用。

沒有關閉 thinking、降低 reasoning effort、砍掉父子 Agent、硬降搜尋結果數、加入付費摘要 Agent，或跨工作流重用可能過時的新聞。這些改動可能影響品質，不能拿來宣稱無損省費。

新聞保存歷史的逐次前綴合計約 108 萬 JSON 字元，其中 search 結果占 48.9%，加上 fetch／本地證據讀取共占 71.1%；87.55% 是同一歷史訊息第二次起被帶入的字元。這只說明重播壓力：舊資料沒有保存每次實際送出的臨時 context 和 schema，不能把這些百分比直接換成計費 token。

## 離線對照與一次真實重測

用基準 commit 的程式和新程式對相同舊歷史做離線投影，保留相同工具 schema：

| 歷史案例 | 請求數 | 舊 JSON 字元 | 新 JSON 字元 | 變化 | 平均共同前綴：舊 → 新 |
|---|---:|---:|---:|---:|---:|
| 協作 c | 25 | 541,382 | 530,899 | −1.94% | 3,883 → 13,380 字元 |
| 新聞 b | 19 | 1,331,605 | 1,241,562 | −6.76% | 3,259 → 55,151 字元 |

這使用固定最終資料庫狀態與重建請求時間，不能還原每次當時的預算／授權狀態；它是相同歷史的反事實比較，不是實際帳單。全部 assistant／reasoning 和工具 ID 保持，原 SQLite／WAL 雜湊未變。明細只存本機 `data/token-audit/context-projection-comparison.json`。

香港時間 22:52:57–22:54:27，只做一次新的完整協作實測，沿用前次的同一目標、模型、low reasoning effort 和預算。`data/live-tests/context-efficiency-20261019/report.json` 為 **PASS**，測試開始時的程式 SHA 與結束時一致。

**本輪確認了快取改善，沒有確認每次任務的總 token 必然下降。** 相同歷史的投影較小，但真實模型走了不同路徑、產生較長輸出，總量反而增加。快取命中仍計入 prompt tokens，也不是免費；未命中輸入下降 57.60% 不能直接當作帳單下降 57.60%。沒有用同一模型反覆重跑直到出現漂亮數字。

增量主要來自孫任務 reviewer：5 → 7 次請求、30,236 → 65,561 tokens。它多讀了兩份已保存的網頁證據，再修訂審查報告，補充規格核對與審查範圍、收回過強措辭；文件由 2,153 增至 4,762 bytes。這不是完全相同的重複寫入，也沒有新網路請求或執行器重試，不能為壓低數字禁止這類核對。coder 少一次請求，researcher 多一次但總量幾乎相同，續輪只增加 427 tokens。

兩階段全部 7 個任務完成，父／子／孫 WORK、並行請求、REPLY、串流、Docker 的固定 8 項外部案例、官方 Search 1 次和 Fetch 2 次都通過。續輪提問後重開資料庫、回答與產物延續通過，沒有新增網頁請求。沒有失敗的模型呼叫、retry 或 repair；所有 27 次請求都有完整 token／cache 計數和只含數字的請求量測。DB integrity 正常、外鍵零違規，容器已清理。

兩個本機 Python 環境（3.12.4、3.14.3）各 **280 項測試通過**，離線 PTY 的父子任務、問答／模擬審批、縮放及恢復也通過。新聞原句這輪只做歷史投影與證據完整性回歸，沒有再次付費搜尋新聞；新實測核對的是官方文件的搜尋／抓取。因此不能由本輪宣稱所有新聞任務品質都已統計等效。

## 重現與驗證口徑

下列命令只讀資料庫並輸出數字統計，不讀 key、不連網、不呼叫模型。輸出路徑必須尚未存在：

```sh
.venv/bin/python scripts/audit_token_usage.py \
  --database collaboration_c data/live-tests/collaboration-web-20261019-c/live.sqlite \
  --database news_b data/live-tests/news-20261019-b/live.sqlite \
  --output data/token-audit/review.json
```

原始用量證據與完整歷史留在本機 `data/`；公開倉庫只包含程式與去除私人內容的彙總文件。新實測需要分別報告總 tokens、未命中輸入、快取覆蓋率、任務品質與調用次數；不能把快取命中當成沒有使用 tokens，也不能把單次隨機生成的差異全歸功於某一項修改。
